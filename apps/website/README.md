# Packages website

`@moldea.ai/packages-website` is the private Astro application that renders the public technical documentation for the open-source moldea packages ecosystem. It is an application under `/apps/**`, not a first-class package, npm artifact, or package-catalog entry. It owns runtime-label guidance and the presentation of declared binding checks.

Its introduction explains the CLI and TypeScript packages as tools for Git-owned project context, decision records, and structural checks. Runtime-agent instructions use the same foundation when needed. The homepage and capabilities page own their visible introduction; `content/getting-started.md` owns the guide and its search metadata, while `src/lib/generation/generation.ts` owns the machine-facing introduction in `llms.txt`. Technical package contracts remain in package-owned documentation and the Repository Format specification.

## Source model

The build discovers immediate public implemented projects from `/projects/**`, validates their manifests and package-owned `docs/**`, derives dependencies from manifests, extracts API reference data from actual public TypeScript exports, and reads `/specifications/repository-format.md`. Runtime IDs, display names, and logo assets come from the public Website UI catalog. This website does not infer SDK compatibility or runtime wiring.

The ignored `.generated/model.json` file is a deterministic build cache. Do not edit it. Package behavior belongs in each project's docs and the Repository Format contract belongs only in `/specifications/repository-format.md`. Model generation reads those sources and executes finite synthetic Core, reader, and CLI examples.

Website UI is intentionally excluded from the visitor-facing package model. Its implementation and repository documentation remain under `projects/website-ui/`, but this website does not publish its overview, error documentation, API reference, search records, sitemap URLs, or `llms.txt` entries.

`/runtimes/` presents all 35 named runtime labels using Website UI's `RuntimeGrid`, explains file and export coverage, and points agent review to installed SDK type definitions. `custom` remains available for another runtime with project-owned guidance. Labels never imply compatibility, certification, or vendor endorsement. The homepage uses the same icon grid. Entries open official runtime websites or repositories with external-link indicators; widely used SDKs and frameworks appear first, with three responsive rows before Load more reveals the complete catalog and disappears. All entries remain available without JavaScript.

`src/lib/redirects/constants.ts` owns a fixed list of 73 retired routes: the adapter directory, custom page, compatibility directory, and each of ten adapter indexes, five documentation slugs, and API page. Cloudflare retains its plural `verified-targets` slug. Astro emits an immediate static redirect to `/runtimes/` for every entry, with noindex, destination canonical, and fallback link. Redirects are excluded from search and sitemap equality. The compatibility JSON endpoint is removed; artifact verification rejects a leftover copy, including under `BASE_PATH`.

`content/getting-started.md` owns the guide's frontmatter, rendered body, and search text. It hands adoption to the Agent Skill, introduces optional Cloud collaboration at `https://moldea.ai`, and links the CLI's canonical documentation. `src/lib/discovery-copy/` owns friendly package labels, validated for complete and non-stale package coverage.

`src/lib/inspection-example/` owns three synthetic repository snapshots: a path resolves, moving its source breaks the binding, and updating that binding restores it. `src/lib/instruction-example/` owns the independent hero example: a customer-support agent uses a delivery-status tool whose implementation file is missing. The preview shows the instruction, the tool's explicit manifest connection, and the missing file. Core validates that declared connection; it does not infer it from the instruction's prose. Generation runs public `createCore` and `createMemoryRepositoryReader` exports and derives visible source content and validation results from those same snapshots. Unexpected results fail generation. The reference-check section shows all three states through `inspection-diagram`, side by side on desktop and stacked on mobile. The architecture overview reuses the moved-file validation and retains the complete native Core result.

The hero, reference-check cards and architecture overview compose Website UI's `InspectionList` and `InspectionDialog` through the app-owned `inspection-result` adapter. One finding is one actionable row with its subject icon, inline severity and exact code. No findings show the concise outcome with View output. Finding shows source-backed evidence; Output shows the complete native validation. The selected title appears once. The same details remain readable inline without JavaScript. Checks never execute in the browser, read visitors' files or imply automatic repair. They verify declared structure, not source semantics.

`createWebsiteModel` is asynchronous and must be awaited by callers; `loadWebsiteModel` synchronously reads its completed output. Model generation has no timestamps or environment-dependent example values. Root `turbo.json` is the authoritative owner of website cache inputs, including repository-owned generation sources outside the app, dependency builds, and `SITE_URL`/`BASE_PATH`. It caches `.generated/model.json` together with `dist/`, so restored content and rendered artifacts agree.

Reusable website foundations come from the public `@moldea.ai/website-ui` workspace package. That package owns shared semantic design tokens, global interaction states, base-path and theme utilities, sanitized Markdown and literal code blocks, optional code-copy controls, the branded hero backdrop, file connection labels, responsive site and documentation shells, local-search behavior, generic tabs and badges, and normalized evaluation replay. This application owns the `https://packages.moldea.ai` origin, `moldea-website-theme` storage key, navigation data, page composition, source validation, package discovery, generated content, and packages-specific copy. The [Website UI composition guidelines](../../projects/website-ui/README.md#composition-guidelines) are authoritative for shared presentation. `CodeCopyControls` is mounted once in the base layout. Search focus is opted into through `LocalSearch`, with no app-owned script accessing its private markup.

## Executable capability catalog

`src/lib/capabilities/` owns the internal catalog generated by `createWebsiteModel`. Its 117 synthetic cases cover all eight Core operations and account for all 86 Core diagnostic codes. Diagnostic coverage distinguishes executed examples from linked documented boundaries. Binding examples pin file existence, passed and failed exports, uncheckable source, warning identity and acceptance, and the `integration` diagnostic group. CommonJS remains not checked. No example claims runtime wiring.

CLI schema 7 examples execute actual commands with successful warning exits, separate outstanding and accepted-warning counts, and retained acceptance reasons. Every case retains `output` separately from its derived summary. Producers capture complete Core responses and native CLI envelopes before projection, including ordered continuation responses; command and process exit status stay outside native JSON. Compound reader operations and refusal facts are labelled execution facts. `capabilities/output` captures JSON without silently omitting fields and verifies full equality, allowing only explicitly declared redactions identified by response index, JSON pointer and reason. Current fixtures need no redactions. `/capabilities/` exposes every executed case across six sections; there is no public capability JSON endpoint.

Core cases use memory snapshots. Reader cases also exercise disposable filesystem snapshots. CLI cases resolve the declared package bin and execute it with Node against an isolated synthetic Git working tree. Generation requires Git 2.30.0 or newer. Temporary workspaces are removed on success and failure; CLI runs verify that files and Git state remain unchanged. Normal fixtures include a minimal synthetic skill installation so integration warnings remain isolated to their own examples. No provider SDKs, credentials, network requests, or visitor repositories participate.

The generators assert actual outcomes before selecting display fields. Reviewed `core-examples/expected-results.ts` pins complete diagnostics; binding examples independently pin their coverage and warning contracts. Changes require reviewing expectations, not automatically accepting new output. Coverage validation rejects missing cases, unsupported claims, and unsafe source references. Byte inputs and malformed Unicode use explicitly identified byte or JSON-string representations. Derived illustration facts stay compact. Complete output retains native identifiers and cursors from synthetic fixtures; only declared redactions may replace fields. It contains no visitor data or credentials.

The catalog is a finite release-owned collection. Each case executes once per model generation and the completed model is reused. Repository FS and CLI are direct build-time workspace dependencies alongside Core and Repository. No deterministic package code is shipped to visitors for these examples.

`catalog.ts` owns six plain-language sections and exactly four `featuredExampleIds` per section. `getCapabilityShowcase` indexes cases once, leads with those four, and appends every remaining case in existing catalog order. It rejects duplicate, missing, and wrongly grouped selections. The opening four prioritize practical relationship checks and workflows over low-level malformed-input cases. Every case is rendered once and enters local search. Compact example buttons show each title and outcome. Opening a button reveals its `capability-card` illustration in the shared dialog; a result-owned nested dialog contains Finding/Output tabs. Clicking a diagnostic opens Finding; results without diagnostics open Output directly. Full output uses the shared copyable JSON `CodeBlock` with build-time highlighting and keyboard-accessible horizontal scrolling. Artifact verification requires complete rendered output equality, separately from the source evidence. At most the case dialog and one finding dialog can be modal; Escape closes the finding first and restores its row, then closes the case and restores its button.

One `capability-section/disclosure.ts` controller reveals four cases per activation. It updates only newly revealed cards, keeps counts in a polite screen-reader-only live region, moves keyboard focus to the first new example button, and preserves pointer reading position. Category coverage stays in search metadata without a visible secondary list. Completed sections leave no empty controls margin. Direct, search, and history fragments reveal the target’s batch and open its illustration dialog. Astro swaps abort page-owned listeners; return navigation initializes once. With no JavaScript, the same illustrations remain readable inline and disclosure controls stay hidden. The page’s pre-paint enhancement marker hides these inline fallbacks when native modal support is available. There is no per-card hydration, duplicated fallback catalog, browser package execution, or data endpoint. Static transfer and DOM still include every case; four visible cards do not imply a four-card download.

`presentation.ts` selects explicit visual families. File and agent diagrams keep their source-backed relationships. Binding examples distinguish passed, failed, and unchecked exports, warnings, and accepted warnings. Source visuals retain malformed text and labelled byte/JSON-string representations without reparsing them. Operation visuals show actual pages, canonical chunks, ranges, selections, and refusals. Only the snapshot case uses the snapshot diagram. Source previews retain at most 12 lines. Result dialogs retain complete output, labelled source excerpts and material limitations. The runtime label directory is available at `/runtimes/`.

Header, footer, and homepage links discover `/capabilities/`. Generation indexes its page, six sections, and all 117 case fragments without full fixtures. Astro emits one canonical sitemap page without fragments. Artifact checks verify every compact outcome, illustration dialog and visual family, result summary and dialog, reference link, and discovery record. They reject missing cases, unsupported outcomes, unknown examples, and private generated output. Full operation and diagnostic coverage remains enforced during generation and integration testing. Browser checks cover batching, final partial batches, focus, fragments/history, Astro return, no-JavaScript access, nested result dismissal and focus restoration, both themes, reduced motion, and 320px through desktop. Deployment-prefix checks use `BASE_PATH`.

Website UI's `FilePreview` owns file-header presentation and filename-preserving paths. Its inspection list/dialog own result hierarchy and interactions. The application adapts native Core and CLI results in `inspection-result/presentation`, retaining ownership of source content and outcome mapping. Repository Format supplies the header's compact “Repo. Format” label below 1280px in desktop navigation; the mobile menu and wider screens keep the full label.

Astro prefetch is disabled with `prefetch: false`. Normal links and client-router navigation remain enabled. Provider-managed speculation is outside this setting. Mastra appears ninth and Eve tenth through the shared runtime catalogue.

## Commands

Run these from the repository root:

| Command                                                        | Purpose                                                                                                                             |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm website:dev`                                             | Generate the content model and run Astro locally.                                                                                   |
| `pnpm website:prepare`                                         | Build CLI and its dependency closure plus Website UI before low-level website tasks.                                                |
| `pnpm docs:generate`                                           | Write the ignored deterministic content model.                                                                                      |
| `pnpm docs:check`                                              | Validate discovery, docs, exports, binding coverage, and routes without writing source.                                             |
| `pnpm website:build`                                           | Generate, build static HTML and the local search index, then validate artifact links.                                               |
| `pnpm website:check`                                           | Run the complete non-browser website verification sequence.                                                                         |
| `pnpm turbo run test:e2e --filter @moldea.ai/packages-website` | Run focused browser accessibility, theme, navigation, search, and 320px overflow checks on an automatically selected loopback port. |
| `pnpm --filter @moldea.ai/packages-website check:links`        | Revalidate an existing production artifact.                                                                                         |

Root `docs:check`, `docs:generate`, `website:dev`, and `website:check` prepare their executable dependencies automatically. Direct `pnpm --filter @moldea.ai/packages-website ...` tasks require `pnpm website:prepare` first. Root `website:build` retains Turbo dependency ordering. Preparation builds ignored dependency artifacts; it does not modify package sources or continuously watch dependency changes.

The uncached website `clean:build` task runs before Turbo executes or restores the website build. It removes only this application's `dist/` and `.generated/`, preventing retired pages from surviving an older cache restore. It leaves dependency output, source files, and Turbo caches intact. A direct application build already regenerates the model and lets Astro replace its static output.

The default build inputs are `SITE_URL=https://packages.moldea.ai` and `BASE_PATH=/`, matching the established custom-domain deployment. Supply both variables through the process environment for another mount point, for example `SITE_URL` set to `https://moldea-ai.github.io` and `BASE_PATH` set to `/packages/`. Internal links, assets, canonical metadata, Open Graph images, sitemap URLs, search results, robots, and `llms.txt` are all derived from these inputs.

Check root build artifacts with `check:links` before running Playwright, because its server setup rebuilds the site. Cache verification must inspect fresh source markers in model and static artifacts immediately after root `website:build`, then confirm an unchanged warm hit. Run clean-command and source-mutation checks in an isolated checkout with its own installation. Alternate-origin verification must retain exact expected metadata URLs and test Turbo-mediated E2E environment forwarding, including `PLAYWRIGHT_BROWSERS_PATH`.

## Design and rendering

The application maps GitHub light-theme comment tokens to Website UI's `muted-foreground` token so highlighted comments meet contrast requirements on the off-white documentation surface. Dark highlighting retains its existing palette.

The application uses Astro static output, Tailwind CSS 4's CSS-first configuration, Ubuntu Sans Variable, and Lucide Astro icons. Website UI supplies the platform-aligned semantic OKLCH tokens, action and link states, accessible breadcrumbs, pre-paint theme initialization, theme controls, local static search, and shared responsive prose primitives. Light and dark themes have distinct token sets, reduced-motion behavior is centralized, and documentation remains ordinary static HTML when JavaScript is disabled.

Every link that opens in a new tab includes the shared external-link indicator. Website UI adds it to rendered Markdown and header source links, while application-authored links use Lucide Astro's `ExternalLink` icon. Production artifact verification rejects a new-tab link without the indicator.

Secondary navigation uses Website UI's ghost `ActionLink`: transparent in light mode, with the existing outline border and translucent surface in dark mode. `src/lib/site` owns the reused dark-theme classes. Primary calls to action, inverted links on dark emphasis sections, and button controls retain their existing variants.

The homepage hero uses Website UI's `py-14 sm:py-18 lg:py-20` insets, matching the platform and Skill homepages. On desktop, the repository-check preview aligns with the vertical center of the complete text column, including its badges and actions. The `See how it works` action uses a down arrow for its same-page destination; `Start using the tools` uses a right arrow for the getting-started page.

Homepages follow the [shared homepage alignment rules](../../../platform/DESIGN.md#layout): side-by-side content columns center by default, substantially taller examples align at the top on desktop without clipping relevant rule text, split section headers align at the bottom on desktop, and icons, controls, and diagram connectors remain centered. Hero copy includes its badges and actions in the centered block. The rule applies at each composition's column breakpoint; stacked mobile content retains its natural height.

Use explicit inline code in authored prose for complete product names, including `moldea`, `moldea Skill`, `moldea Agent Skill`, and `moldea Cloud`. Keep complete technical tokens together, including package names, commands, paths, identifiers, and literals. When a surface cannot render inline code, use the complete name or token as plain text. Titles and matching H1s, navigation, metadata, accessible strings, artwork, and actions remain plain. Preserve recorded conversations and source payloads. Never decorate only the brand substring within a larger token; callers must not infer code semantics from a brand match. The homepage and Capabilities page use the app layout's `flushFooter` option because their final full-width sections already own closing spacing; documentation pages retain the shared footer spacing.

The structural check, Repository Format, and runtime sections follow the platform and skill's split headers: title left, description right and bottom-aligned on large screens, stacked on smaller screens. The hero and guide introductions retain stacked copy. The branded square backdrop is reserved for the homepage hero; Capabilities and documentation routes use the normal page background. Code blocks follow Website UI's shared policy: preserve code and structured output, wrap only explicitly labelled plain text, and offer copy controls unless the block contains an illustrative or incomplete excerpt. The Minimum repository example uses Website UI's shared YAML `CodeBlock` and standard copy toolbar, matching the specification's YAML blocks. Complete native output remains copyable; labelled source excerpts opt out. Complete commands, Markdown examples, and reusable source remain copyable. The app-owned Project footer includes Cloud at `https://moldea.ai` using the shared `plain-link` states.

Every indexable page publishes a unique title and description, an absolute self-canonical URL, complete Open Graph and Twitter image metadata, and Schema.org breadcrumbs. The canonical root also publishes the `WebSite` identity used for the search-result site name, with a description derived from the same page metadata. Subdirectory deployments omit that domain-level identity. Production artifact verification requires the sitemap to match the complete canonical page set and rejects duplicate metadata, malformed or inconsistent structured data, noindex sitemap entries, and missing social-card fields. Social-image alternative text describes the existing logo and tagline.

Page-local tests use Astro's native underscore exclusion, such as `src/pages/getting-started/_index.test-e2e.ts`. The prefix is the framework-specific exception to ordinary source-derived test naming: Astro ignores the route, Playwright still discovers the test, and TypeScript still checks it. Artifact verification rejects emitted test filenames and verifies the guide, search/LLM handoffs, and real example states. A Vite preview server's fallback status is not proof that a route was or was not emitted.

The sibling platform repository is a design and specification reference only. The build never imports it, links it as a workspace, fetches private files, or requires it in CI.

## Deployment

Pull requests build and verify the site without deploying it. Reusable repository CI selects this application for website, Website UI, specification, or transitive runtime inputs. Its selected build runs `createWebsiteModel` and artifact validation; the duplicate standalone CI `docs:check` invocation is omitted. The root consistency checks remain always on, including website-only changes. Selected tests run without dependency tests; the independent Pages workflow retains its complete website verification and availability gates. Relevant pushes to `main`, including standalone Repository Format specification and private-package source changes, rebuild from the exact pushed commit, read the configured host and base path from GitHub Pages, build the canonical HTTPS origin from that host, pass those values to Astro and the artifact checks, upload `apps/website/dist` with GitHub's official Pages artifact action, and deploy through the `github-pages` environment. Colocated workflow tests under `.github/workflows/` run in the root unit suite and verify coverage of the repository-level website build inputs. After deployment, the workflow submits `https://packages.moldea.ai/sitemap-index.xml` to the `sc-domain:moldea.ai` Google Search Console property. The workflow is separate from npm publication.

If Pages has never been enabled, a repository owner must once select **GitHub Actions** under **Settings → Pages → Build and deployment → Source**. Normal publication is automatic after that setting; no recurring manual dispatch or artifact promotion is required.

Search Console submission authenticates with the `GOOGLE_SEARCH_CONSOLE_CREDENTIALS` organization-level Actions secret, with this repository included in its selected-repository policy. The secret contains the JSON key for `moldea-sitemap-submitter@moldea-prod.iam.gserviceaccount.com`, which must remain an owner of the Search Console property and retain `Service Account Token Creator` on itself. Manual workflow dispatches do not submit the sitemap. A submission failure leaves the deployed Pages artifact live and fails only the post-deployment submission job.
