# Packages website

`@moldea.ai/packages-website` is the private Astro application that renders the public technical documentation for the open-source `moldea` packages ecosystem. It is an application under `/apps/**`, not a first-class package, npm artifact, or package-catalog entry. It owns the public maturity assigned to each runtime target.

Its introduction explains the CLI and TypeScript packages as tools for Git-owned project context, decision records, and structural checks. Runtime-agent instructions and adapters extend that foundation when needed. The homepage and capabilities page own their visible introduction; `content/getting-started.md` owns the guide and its search metadata, while `src/lib/generation/generation.ts` owns the machine-facing introduction in `llms.txt`. Technical package contracts remain in package-owned documentation and the Repository Format specification.

## Source model

The build discovers immediate public implemented projects from `/projects/**`, validates their manifests and package-owned `docs/**`, derives dependencies from manifests, extracts API reference data from actual public TypeScript exports, reads the official Repository Format source from `/specifications/repository-format.md`, and reads technical adapter compatibility and optional skill-owned qualification links through the repository's strict parser for `compatibility/runtimes.yaml`. Target maturity is edited in `content/runtime-target-maturity.yaml`; generation fails unless that file contains exactly one maturity for every matrix target and no stale targets. The generated UI and `https://packages.moldea.ai/compatibility/runtimes.json` use the same combined publication model.

The ignored `.generated/model.json` file is a deterministic build cache. Do not edit it. Package behavior belongs in each project's docs, the Repository Format contract belongs only in `/specifications/repository-format.md`, technical adapter compatibility belongs in the matrix, and target maturity belongs in the website content file. Updating and deploying the maturity YAML file is the complete maturity-management workflow. The public JSON publication uses schema version `1`, identifies technical matrix version `2`, recursively orders object keys, normalizes unordered collections, and contains no generated timestamp or installed CLI state.

Website UI is intentionally excluded from the visitor-facing package model. Its implementation and repository documentation remain under `projects/website-ui/`, but this website does not publish its overview, error documentation, API reference, search records, sitemap URLs, or `llms.txt` entries.

`/adapters/` is the combined runtime and compatibility directory. Compact rows link each target to its exact scope on the existing adapter page; descriptions and full adapter details are not repeated in the directory. Experimental and deprecated links use amber and red semantic tones with explicit status text. Each adapter detail target has its own maturity badge beside its heading, without a separate legend. `/compatibility/` remains an Astro-generated immediate static redirect to `/adapters/`, with a noindex directive, destination canonical, and fallback link. It is absent from the sitemap and search index. `/compatibility/runtimes.json` is unchanged. Artifact verification checks this redirect separately from content-page SEO, including deployments under `BASE_PATH`.

`content/getting-started.md` owns the guide's frontmatter, rendered body, and search text. It hands adoption to the Agent Skill, introduces optional Cloud collaboration at `https://moldea.ai`, and links the CLI's canonical documentation without copying installation commands. `src/lib/discovery-copy/` owns friendly package, runtime, and target labels, validated for complete and non-stale canonical ID coverage. This presentation metadata never changes the compatibility JSON contract.

`src/lib/inspection-example/` owns three synthetic repository snapshots: a path resolves, moving its source breaks the binding, and updating that binding restores it. `src/lib/instruction-example/` owns the independent hero example: a customer-support agent uses a delivery-status tool whose implementation file is missing. The preview shows the instruction, the tool's explicit manifest connection, and the missing file. Core validates that declared connection; it does not infer it from the instruction's prose. Generation runs public `createCore` and `createMemoryRepositoryReader` exports and derives visible source content and validation results from those same snapshots. Unexpected results fail generation. The reference-check section shows all three states through `inspection-diagram`, side by side on desktop and stacked on mobile. The architecture overview reuses the moved-file validation excerpt, including error and warning counts, and identifies the omitted Core fields beside the JSON.

The hero, reference-check cards, and result-dialog headings share `inspection-summary` for identical outcome copy and consistent icon and text proportions. Their optional “View result” controls use `inspection-result`, which composes Website UI's dialog heading slot and compact status badges. The dialog retains the summary's description, with status beside its heading and highlighted validation JSON below. Its badged icon is hidden below `sm` (640px), while card icons remain visible at every width. Both examples remain readable without opening a dialog or enabling JavaScript; checks never execute in the browser. They verify declared structure, not source semantics, do not read visitors' files, and do not imply automatic repair.

`createWebsiteModel` is asynchronous and must be awaited by callers; `loadWebsiteModel` synchronously reads its completed output. Model generation has no timestamps or environment-dependent example values. Root `turbo.json` is the authoritative owner of website cache inputs, including repository-owned generation sources outside the app, dependency builds, and `SITE_URL`/`BASE_PATH`. It caches `.generated/model.json` together with `dist/`, so restored content and rendered artifacts agree.

Reusable website foundations come from the public `@moldea.ai/website-ui` workspace package. That package owns shared semantic design tokens, global interaction states, base-path and theme utilities, sanitized Markdown and literal code blocks, optional code-copy controls, the branded hero backdrop, file connection labels, responsive site and documentation shells, local-search behavior, generic tabs and badges, and normalized evaluation replay. This application owns the `https://packages.moldea.ai` origin, `moldea-website-theme` storage key, navigation data, page composition, source validation, package discovery, generated content, and packages-specific copy. The [Website UI composition guidelines](../../projects/website-ui/README.md#composition-guidelines) are authoritative for shared presentation. `CodeCopyControls` is mounted once in the base layout. Search focus is opted into through `LocalSearch`, with no app-owned script accessing its private markup.

## Executable capability catalog

`src/lib/capabilities/` owns the internal catalog generated by `createWebsiteModel`. Its 151 synthetic cases cover all eight Core operations, account for all 82 Core diagnostic codes, and provide source witnesses for all 101 full/partial patterns across 14 runtime targets. Diagnostic coverage distinguishes executed examples from linked documented boundaries. The CLI schema 6 consumer executes a version-dependent warning case with a successful exit, complete counts, severity, and safe version details; runtime examples separately preserve the distinction between an unverified relationship and a confirmed error. CLI result dialogs retain the envelope and nested `page.records` shape, omit fields and records only as labelled excerpts, and show the process exit status outside the JSON. Generation rejects excerpt fields or values that differ from the executed response. Reader and inspection dialogs label their custom summaries as selected execution facts rather than package responses. Target ranges, technical support, maturity, and qualification links come from the existing publication model, not a separate support inventory. `/capabilities/` exposes every one of these executed cases across six sections; there is no public capability JSON endpoint.

Core and adapter cases use memory snapshots. Reader cases also exercise disposable filesystem snapshots. CLI cases resolve the declared package bin and execute it with Node against an isolated synthetic Git working tree. Generation therefore requires Git 2.30.0 or newer, in addition to the repository's Node and pnpm prerequisites. Temporary workspaces are removed on success and failure; CLI runs verify that fixture files and Git state remain unchanged. Illustrated provider source is inspected, never imported or executed. No provider SDKs, credentials, network requests, or visitor repositories participate.

The generators assert actual outcomes before selecting display fields. Reviewed `core-examples/expected-results.ts` and `runtime-examples/expected-results.ts` pin complete diagnostics and runtime evidence; source witnesses distinguish syntax forms that produce equivalent evidence. Changes to examples or package behavior require reviewing these expectations, not automatically regenerating them to accept new output. Coverage validation rejects missing cases, stale targets/patterns, unsupported claims, and unsafe source references. Byte inputs and malformed Unicode use explicitly identified byte or JSON-string representations; ordinary excerpts retain their executed logical path. Published facts omit opaque reader identities, cursors, host paths, and process context.

The catalog is a finite, release-owned collection, not an accumulating user dataset. Each distinct case executes once per model generation and the resulting model is reused. Repository FS, CLI, and all ten adapters are direct build-time workspace dependencies alongside Core and Repository. No deterministic package code is shipped to visitors for these examples.

`catalog.ts` owns six plain-language sections and exactly four `featuredExampleIds` per section. `getCapabilityShowcase` indexes cases once, leads with those four, and appends every remaining case in existing catalog order. It rejects duplicate, missing, and wrongly grouped selections. Every case is rendered once and enters local search. Inline `capability-card` visuals explain the result before the optional, single-layer result dialog. The result excerpt uses plain text rendering with explicit scrolling to avoid syntax-token markup for every hidden dialog.

One `capability-section/disclosure.ts` controller reveals four cases per activation. It updates only newly revealed cards, keeps category counts polite, moves keyboard focus to the first new heading, and preserves pointer reading position. Direct, search, and history fragments reveal the target’s batch. Astro swaps abort page-owned listeners; return navigation initializes once. With no JavaScript, the same complete catalog stays readable and disclosure controls stay hidden. There is no per-card hydration, duplicated fallback catalog, browser package execution, or data endpoint. Static transfer and DOM still include every case; four visible cards do not imply a four-card download.

`presentation.ts` selects explicit visual families. File and agent diagrams keep their source-backed relationships; supported runtime source stays distinct from absent evidence. Source visuals retain malformed text and labelled byte/JSON-string representations without reparsing them. Operation visuals show actual pages, canonical chunks, ranges, selections, and refusals. Only the snapshot case uses the snapshot diagram. Runtime previews select existing pattern witnesses, independently of warning locations, and retain at most 16 contiguous source lines per preview; general source previews retain at most 12. Result dialogs hold ownership, labelled excerpts, and material limitations. The complete runtime directory remains on Adapters.

Header, footer, and homepage links discover `/capabilities/`. Generation indexes its page, six sections, and all 151 case fragments without full fixtures. Astro emits one canonical sitemap page without fragments. Artifact checks verify every inline visual family, outcome label and summary, result dialog, reference link, and discovery record. They reject missing cases, unsupported outcomes, unknown examples, and private generated output. Full operation, diagnostic, runtime-pattern, and source-witness coverage remains enforced during generation and integration testing. Browser checks cover batching, final partial batches, focus, fragments/history, Astro return, no-JavaScript access, single-layer result dismissal, both themes, reduced motion, and 320px through desktop. Deployment-prefix checks use `BASE_PATH`.

Website UI's `FilePreview` owns file-header presentation and filename-preserving paths. Its `ResultSummary` owns the shared icon/title/description proportions in cards and dialog headings. The application composes these exports in `repository-check-preview` and `inspection-summary`, retaining ownership of source content and Core outcome mapping. Repository Format supplies the header's compact “Repo. Format” label below 1280px in desktop navigation; the mobile menu and wider screens keep the full label.

## Commands

Run these from the repository root:

| Command                                                        | Purpose                                                                                                                             |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm website:dev`                                             | Generate the content model and run Astro locally.                                                                                   |
| `pnpm website:prepare`                                         | Build CLI and its dependency closure plus Website UI before low-level website tasks.                                                |
| `pnpm docs:generate`                                           | Write the ignored deterministic content model.                                                                                      |
| `pnpm docs:check`                                              | Validate discovery, docs, exports, adapters, and routes without writing source.                                                     |
| `pnpm website:build`                                           | Generate, build static HTML and the local search index, then validate artifact links.                                               |
| `pnpm website:check`                                           | Run the complete non-browser website verification sequence.                                                                         |
| `pnpm turbo run test:e2e --filter @moldea.ai/packages-website` | Run focused browser accessibility, theme, navigation, search, and 320px overflow checks on an automatically selected loopback port. |
| `pnpm --filter @moldea.ai/packages-website check:links`        | Revalidate an existing production artifact.                                                                                         |

Root `docs:check`, `docs:generate`, `website:dev`, and `website:check` prepare their executable dependencies automatically. Direct `pnpm --filter @moldea.ai/packages-website ...` tasks require `pnpm website:prepare` first. Root `website:build` retains Turbo dependency ordering. Preparation builds ignored dependency artifacts; it does not modify package sources or continuously watch dependency changes.

The uncached website `clean:build` task runs before Turbo executes or restores the website build. It removes only this application's `dist/` and `.generated/`, preventing retired pages from surviving an older cache restore. It leaves dependency output, source files, and Turbo caches intact. A direct application build already regenerates the model and lets Astro replace its static output.

The default build inputs are `SITE_URL=https://packages.moldea.ai` and `BASE_PATH=/`, matching the established custom-domain deployment. Supply both variables through the process environment for another mount point, for example `SITE_URL` set to `https://moldea-ai.github.io` and `BASE_PATH` set to `/packages/`. Internal links, assets, canonical metadata, Open Graph images, sitemap URLs, search results, robots, and `llms.txt` are all derived from these inputs.

Check root build artifacts with `check:links` before running Playwright, because its server setup rebuilds the site. Cache verification must inspect fresh source markers in model and static artifacts immediately after root `website:build`, then confirm an unchanged warm hit. Run clean-command and source-mutation checks in an isolated checkout with its own installation. Alternate-origin verification must retain exact expected metadata URLs and test Turbo-mediated E2E environment forwarding, including `PLAYWRIGHT_BROWSERS_PATH`.

## Design and rendering

The application uses Astro static output, Tailwind CSS 4's CSS-first configuration, Ubuntu Sans Variable, and Lucide Astro icons. Website UI supplies the platform-aligned semantic OKLCH tokens, action and link states, accessible breadcrumbs, pre-paint theme initialization, theme controls, local static search, and shared responsive prose primitives. Light and dark themes have distinct token sets, reduced-motion behavior is centralized, and documentation remains ordinary static HTML when JavaScript is disabled.

Every link that opens in a new tab includes the shared external-link indicator. Website UI adds it to rendered Markdown and header source links, while application-authored links use Lucide Astro's `ExternalLink` icon. Production artifact verification rejects a new-tab link without the indicator.

Secondary navigation uses Website UI's ghost `ActionLink`: transparent in light mode, with the existing outline border and translucent surface in dark mode. `src/lib/site` owns the reused dark-theme classes. Primary calls to action, inverted links on dark emphasis sections, and button controls retain their existing variants.

The homepage hero uses Website UI's `py-14 sm:py-18 lg:py-20` insets, matching the platform and Skill homepages. On desktop, the repository-check preview aligns with the vertical center of the complete text column, including its badges and actions. The `See how it works` action uses a down arrow for its same-page destination; `Start using the tools` uses a right arrow for the getting-started page.

Homepages follow the [shared homepage alignment rules](../../../platform/DESIGN.md#layout): side-by-side content columns align at their vertical centers, split section headers align at the bottom on desktop, and icons, controls, and diagram connectors remain centered. Hero copy includes its badges and actions in the centered block. The rule applies at each composition's column breakpoint; stacked mobile content retains its natural height.

Standalone `moldea` references in visible text use inline code: compose Website UI's `InlineBrandText` for authored or dynamic text and use `productNameTreatment: 'code'` for Markdown. Author complete product names such as `moldea Agent Skill` and `moldea Cloud` as one inline-code span in Markdown, including inside link labels, so their typography stays consistent. Shared breadcrumbs, documentation navigation, header labels, and local-search output apply the same safe rendering to their visible string labels. Metadata, accessible labels, and the logo remain plain text or branding assets as appropriate. The homepage and Capabilities page use the app layout's `flushFooter` option because their final full-width sections already own closing spacing; documentation pages retain the shared footer spacing.

The structural check, Repository Format, and runtime sections follow the platform and skill's split headers: title left, description right and bottom-aligned on large screens, stacked on smaller screens. The hero and guide introductions retain stacked copy. The branded square backdrop is reserved for the homepage hero; Capabilities and documentation routes use the normal page background. Code blocks follow Website UI's shared policy: preserve code and structured output, wrap only explicitly labelled plain text, and offer copy controls unless the block contains an illustrative or incomplete excerpt. The Minimum repository example uses Website UI's shared YAML `CodeBlock` and standard copy toolbar, matching the specification's YAML blocks. The homepage validation excerpt and capability-result excerpts opt out. Complete commands, Markdown examples, and reusable source remain copyable. The app-owned Project footer includes Cloud at `https://moldea.ai` using the shared `plain-link` states.

Every indexable page publishes a unique title and description, an absolute self-canonical URL, complete Open Graph and Twitter image metadata, and Schema.org breadcrumbs. The canonical root also publishes the `WebSite` identity used for the search-result site name, with a description derived from the same page metadata. Subdirectory deployments omit that domain-level identity. Production artifact verification requires the sitemap to match the complete canonical page set and rejects duplicate metadata, malformed or inconsistent structured data, noindex sitemap entries, and missing social-card fields. Social-image alternative text describes the existing logo and tagline.

Page-local tests use Astro's native underscore exclusion, such as `src/pages/getting-started/_index.test-e2e.ts`. The prefix is the framework-specific exception to ordinary source-derived test naming: Astro ignores the route, Playwright still discovers the test, and TypeScript still checks it. Artifact verification rejects emitted test filenames and verifies the guide, search/LLM handoffs, and real example states. A Vite preview server's fallback status is not proof that a route was or was not emitted.

The sibling platform repository is a design and specification reference only. The build never imports it, links it as a workspace, fetches private files, or requires it in CI.

## Deployment

Pull requests build and verify the site without deploying it. Relevant pushes to `main`, including standalone Repository Format specification and private-package source changes, rebuild from the exact pushed commit, read the configured host and base path from GitHub Pages, build the canonical HTTPS origin from that host, pass those values to Astro and the artifact checks, upload `apps/website/dist` with GitHub's official Pages artifact action, and deploy through the `github-pages` environment. Colocated workflow tests under `.github/workflows/` run in the root unit suite and verify coverage of the repository-level website build inputs. After deployment, the workflow submits `https://packages.moldea.ai/sitemap-index.xml` to the `sc-domain:moldea.ai` Google Search Console property. The workflow is separate from npm publication.

If Pages has never been enabled, a repository owner must once select **GitHub Actions** under **Settings → Pages → Build and deployment → Source**. Normal publication is automatic after that setting; no recurring manual dispatch or artifact promotion is required.

Search Console submission authenticates with the `GOOGLE_SEARCH_CONSOLE_CREDENTIALS` organization-level Actions secret, with this repository included in its selected-repository policy. The secret contains the JSON key for `moldea-sitemap-submitter@moldea-prod.iam.gserviceaccount.com`, which must remain an owner of the Search Console property and retain `Service Account Token Creator` on itself. Manual workflow dispatches do not submit the sitemap. A submission failure leaves the deployed Pages artifact live and fails only the post-deployment submission job.
